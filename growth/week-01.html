讲义 · 四栏卡片

是什么

Anthropic 把“代理式系统”分为两类：工作流（LLM 和工具按预先写好的代码路径编排）和代理（LLM 自己决定流程和工具使用）。来源 ↗

文中的说法：代理“通常只是在循环里、根据环境反馈使用工具的 LLM”，每一步都要从环境拿到“ground truth”（如工具调用结果、代码执行结果）来判断进展，并常设最大迭代次数等停止条件。来源 ↗

对编码代理来说，这个循环就是：读需求 → 读代码/搜索 → 改文件 → 跑测试或编译 → 看结果 → 再改，直到完成或需要人决策。

为什么这样设计

文章建议先用最简单的方案，只在确有收益时增加复杂度；代理用延迟和成本换效果。来源 ↗

编码是代理的好场景，原因文中列了：代码可以用自动化测试验证、代理能用测试结果迭代、问题结构清晰、产出质量可客观衡量。来源 ↗

工具设计（文中称 ACI，代理-计算机接口）要像设计人机界面一样用心。例子：他们发现模型在切换目录后用相对路径容易出错，于是改成工具只接受绝对路径，问题消失。来源 ↗

规则文件的作用：Claude Code 每次会话都从全新上下文开始，CLAUDE.md 是你写下的持久指令，每次会话开头加载。来源 ↗

什么时候会出问题

  • 错误累积：自主性带来更高成本和“错误叠加”的风险，文章建议在沙箱里充分测试并加护栏。来源 ↗
  • 规则不被遵守：官方说明 CLAUDE.md 是“上下文，不是强制配置”，含糊或互相矛盾的指令可能被任选其一；要强制拦截某个操作应该用 hook（如 PreToolUse）。来源 ↗
  • 规则文件太长：官方建议每个 CLAUDE.md 控制在 200 行以内，越长越占上下文、遵守度越低。来源 ↗
  • 框架遮蔽底层：框架多一层抽象，会让底层 prompt 和响应难以调试；对“底层到底做了什么”的错误假设是常见错误来源。来源 ↗
  • 上下文窗口与成本：每轮循环都把历史、文件内容、工具结果放进上下文，任务越长越贵、越容易丢失早期信息。具体窗口大小和价格因模型而异，这里不写数字（未核实）。

怎么验证过

完成本周实验后，在卡片里写下：有/无规则文件时，代理生成代码的 3 处具体差异；规则里哪一条没被遵守，你怎么改写后被遵守了。没做完实验之前，这一栏保持空白。

周末动手实验（半天）

  1. 找一个小的 Java 项目（Spring Boot 或纯 Maven 均可），确保 mvn test 能跑通。
  2. 无规则基线：不放任何规则文件，让 Claude Code（或 Cursor）完成一个小需求，例如“新增一个按名字查询用户的接口并写单测”。保存 diff。
  3. 加规则：在项目根目录写 CLAUDE.md（或 Cursor 的规则文件），写 5–10 条可验证的规则，例如“构建命令是 mvn -q test”“Controller 放在 …/web 包”“禁止使用 field 注入，用构造器注入”“每个新接口必须有单测”。官方建议写成具体可检查的句子。来源 ↗
  4. 在 Claude Code 里运行 /context，确认 CLAUDE.md 出现在 Memory files 列表里。来源 ↗
  5. 新开会话，用同样的需求再跑一次，保存 diff。
  6. 对比两份 diff：包结构、注入方式、测试是否生成、是否自己跑了测试。记下哪条规则没被遵守，改写后再试一次。

回忆题

  1. 工作流和代理的区别是什么？
    参考答案

    工作流：LLM 和工具按预先写好的代码路径编排；代理：LLM 自己动态决定流程和工具使用。

  2. 为什么说编码是代理的好场景？
    参考答案

    代码可用自动化测试验证，代理可以用测试结果迭代；问题结构清晰；质量可客观衡量。

  3. 代理每一步为什么要拿“环境反馈”？
    参考答案

    要靠工具结果或代码执行结果这类真实信息判断进展，否则错误会叠加；同时设最大迭代次数等停止条件。

  4. CLAUDE.md 写了规则，代理却没遵守，可能原因和对策？
    参考答案

    CLAUDE.md 只是上下文不是强制配置；规则含糊、互相矛盾或文件过长都会降低遵守度。对策：写具体可验证的句子、保持短小、用 /context 确认已加载；必须拦截的操作用 hook。

  5. 举一个“好的工具设计”的例子。
    参考答案

    文中例子：模型在切换目录后用相对路径出错，把工具改成只接受绝对路径后就不再出错。思路是让工具更难被用错（poka-yoke）。
