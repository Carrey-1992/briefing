模块2 · kube-scheduler 调度器

建议第 2 周完成 · 工作日每天 30 分钟读讲义 · 周末前半天做实验 · 已完成 0 项

目标

能讲清 kube-scheduler 的“过滤 → 打分 → 绑定”；知道 requests 而不是实际用量决定能否调度；会用 describe/events 定位 Pending 原因；理解亲和、污点容忍、优先级抢占和调度框架扩展点各解决什么问题。

讲义 · 四栏卡片（读完一栏点 ✓）

是什么

kube-scheduler 监视新建且未分配节点的 Pod，为每个 Pod 找最合适的节点。满足要求的节点称为可行节点（feasible nodes）；没有可行节点时 Pod 保持未调度（Pending），直到能放下。选点分两步：过滤（Filtering）找可行节点，打分（Scoring）给可行节点排序，选最高分；然后把决定通知 API Server，这一步叫绑定（binding）。kube-scheduler ↗

调度框架把流程拆成扩展点：PreEnqueue、QueueSort、PreFilter、Filter、PostFilter、PreScore、Score、NormalizeScore、Reserve、Permit、PreBind、Bind、PostBind。每次调度分为调度周期（串行）和绑定周期（可并发）。调度框架（Scheduling Framework） ↗

为什么这样设计

requests 决定调度：调度器只看节点可分配量与已调度 Pod 的 requests 之和，不看实际用量；limits 由 kubelet/运行时在运行期限制。容器资源管理（requests/limits） ↗

约束分层：nodeSelector/节点亲和描述“Pod 想去哪”，Pod 亲和/反亲和描述“和谁放一起/分开”；把 Pod 分配到节点（亲和/反亲和） ↗污点反过来让节点“排斥”Pod，只有带匹配容忍的 Pod 才能上去，适合专用节点（如 GPU 节点）。污点与容忍 ↗

优先级与抢占：放不下时，抢占逻辑找一个节点，驱逐其上优先级更低的 Pod 来腾地方。Pod 优先级与抢占 ↗

扩展点让你用插件定制，而不用 fork 整个调度器。调度框架（Scheduling Framework） ↗

什么时候会出问题

  • requests 写太大：节点明明很闲，Pod 却 Pending；写太小则节点超卖、运行期争抢。容器资源管理（requests/limits） ↗
  • 绕过调度器：手动设 spec.nodeName 会绕过调度器，污点等检查都不生效。污点与容忍 ↗
  • 硬亲和/反亲和过严：requiredDuringScheduling 规则找不到满足的节点就永远 Pending。把 Pod 分配到节点（亲和/反亲和） ↗
  • NoExecute 污点：会驱逐节点上已运行且不容忍的 Pod，不只是阻止新调度。污点与容忍 ↗
  • 抢占误伤：高优先级 Pod 一多，低优先级批任务会被反复驱逐。Pod 优先级与抢占 ↗

怎么验证过

实验后填写：① 把 Pending Pod 的 Events 原文抄下来，解释每个“0/N nodes are available”后面的原因；② 污点加上/去掉前后，Pod 状态如何变化；③ 打分阶段你观察不到，想一想怎么验证（提示：调高调度器日志级别，未核实具体方法）。

动手实验（家里电脑，周末半天）

以下命令未在本机运行验证。建议用多节点 kind 集群，方便观察调度。

# kind 多节点配置 kind-3.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
kind create cluster --name sched --config kind-3.yaml
kubectl get nodes        # 记下两个 worker 节点名，下面用 <w1> <w2> 代替

1. 构造 Pending：requests 超过任何节点

cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: big}
spec:
  containers:
  - name: c
    image: nginx
    resources: {requests: {cpu: "100", memory: "1Gi"}}
EOF
kubectl get pod big            # STATUS 应为 Pending
kubectl describe pod big       # 看最底部 Events 的 FailedScheduling 原因
kubectl get events --field-selector involvedObject.name=big

2. 污点与容忍

kubectl taint nodes <w1> dedicated=gpu:NoSchedule
kubectl taint nodes <w2> dedicated=gpu:NoSchedule
kubectl run t1 --image=nginx           # 应 Pending（control-plane 默认也有污点）
kubectl describe pod t1 | tail -5
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: t2}
spec:
  tolerations:
  - {key: dedicated, operator: Equal, value: gpu, effect: NoSchedule}
  containers: [{name: c, image: nginx}]
EOF
kubectl get pod -o wide                # t2 能调度上去
kubectl taint nodes <w1> dedicated=gpu:NoSchedule-   # 去掉污点，观察 t1

未核实：kind 的 control-plane 节点默认是否带 NoSchedule 污点，用 kubectl describe node 自查。

3. 节点亲和（硬性）

kubectl label nodes <w2> disk=ssd
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata: {name: aff}
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchExpressions:
          - {key: disk, operator: In, values: [ssd]}
  containers: [{name: c, image: nginx}]
EOF
kubectl get pod aff -o wide   # 若 <w2> 仍有污点则 Pending，想想为什么

4.（选做）优先级与抢占

按 Pod 优先级与抢占 ↗ 创建两个 PriorityClass，先用低优先级 Pod 占满一个节点的 CPU requests，再提交高优先级 Pod，观察低优先级 Pod 被驱逐。

实验完成

产出：抄下 3 种 FailedScheduling 原因并逐一解释

回忆题（先答再展开）

  1. kube-scheduler 选节点的两步是什么？选完之后叫什么？
    参考答案

    过滤（找可行节点）和打分（给可行节点排序取最高分）；把结果通知 API Server 的步骤叫绑定。

  2. 节点 CPU 实际使用率只有 10%，为什么 Pod 还是 Pending？
    参考答案

    调度器按 requests 之和与节点可分配量比较，不看实际用量；已调度 Pod 的 requests 总和可能已占满。

  3. 污点/容忍和节点亲和有什么区别？
    参考答案

    亲和是 Pod 主动“想去”某些节点；污点是节点主动“排斥”不容忍的 Pod。容忍只表示“允许去”，不保证一定去，常和亲和配合实现专用节点。

  4. NoSchedule 和 NoExecute 区别？
    参考答案

    NoSchedule 只阻止新的不容忍 Pod 调度上来；NoExecute 还会驱逐已在运行且不容忍的 Pod。

  5. 如果想按自定义规则给节点打分，应该改哪？
    参考答案

    写调度框架插件，实现 Score（必要时 PreScore/NormalizeScore）扩展点，通过调度器配置启用，而不是修改调度器源码主流程。
