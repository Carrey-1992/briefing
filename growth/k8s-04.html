模块4 · 批任务与异构资源

建议第 4 周完成 · 工作日每天 30 分钟读讲义 · 周末前半天做实验 · 已完成 0 项

目标

能讲清 Job/CronJob 语义；设备插件如何把 GPU 变成 nvidia.com/gpu 这类可调度扩展资源及其限制；为什么需要 Kueue/Volcano 这类队列与批调度；在 kind 上用 Kueue 让 Job 排队。

讲义 · 四栏卡片（读完一栏点 ✓）

是什么

Job 创建一个或多个 Pod 并重试直到指定数量成功完成；CronJob 按 cron 时间表周期性创建 Job。Job ↗ CronJob ↗

设备插件：通过 kubelet 的 Registration gRPC 服务注册，向 kubelet 报告它管理的设备，kubelet 在节点状态里通告资源（如 2 个 hardware-vendor.example/foo），之后 Pod 可以像申请 CPU 一样申请。设备插件（Device Plugins） ↗装好厂商插件后集群就有 nvidia.com/gpu、amd.com/gpu 这类可调度资源。调度 GPU ↗

Kueue：K8s 原生的作业排队系统，管理配额以及作业如何消耗配额，决定作业何时等待、何时准入（允许创建 Pod）、何时被抢占；它装在原生集群上，不替换现有组件。Kueue 概览 ↗核心对象：ResourceFlavor（资源种类，可用 nodeLabels 对应不同节点）、ClusterQueue（定义配额）、LocalQueue（命名空间内的提交入口，用户不能直接提交到 ClusterQueue）。Kueue：管理集群配额 ↗

Volcano：CNCF 的容器批调度项目，支持 Spark、PyTorch、Ray 等框架，提供异构设备调度、拓扑感知、多集群调度等能力。Volcano 文档 ↗

为什么这样设计

默认调度器按单个 Pod 调度，不懂“这个作业整体该不该开始”。Kueue 在 Pod 创建前决定准入：它通过 webhook 自动管理 Job 的 suspend 状态，配额够了才放行，所以你不用手动把 Job 建成挂起状态。Kueue：运行 Job ↗

扩展资源只能是整数，不能超卖；GPU 只应写在 limits 里：只写 limits 时以 limits 作为 requests；两者都写必须相等；不能只写 requests。给容器分配扩展资源 ↗ 调度 GPU ↗

未核实：“容器之间不共享 GPU、不能申请小数”是常见说法，本次读的 GPU 页面未找到原句。

一句话对比 Slurm：Slurm 是面向 Linux 集群的开源集群管理与作业调度系统，自带资源分配与排队；K8s + Kueue/Volcano 是在容器编排之上补齐批调度。Slurm 概览 ↗

什么时候会出问题

  • Pod 逐个调度导致死锁：分布式训练要 N 个 Pod 同时到位，默认调度器可能只放上一部分，占着 GPU 空等。Volcano 文档把这类需求列为批调度的动机。Volcano 文档 ↗

    • 未核实：“部分调度占资源空等”是批调度通识，Volcano 首页只列出了需求，未逐字核对 gang 调度说明。

  • 未写 requests：Kueue 依赖 requests 计算配额；只写 limits 时把 limits 当 requests。Kueue：运行 Job ↗
  • GPU 申请写法错误：只写 requests 不写 limits，不符合限制。调度 GPU ↗
  • Job 失败重试：backoffLimit 用尽后 Job 失败，需要看 Pod 日志而不是只看 Job 状态。Job ↗

怎么验证过

实验后填写：① Kueue 下第二个 Job 等待时，Job 和 Workload 分别是什么状态；② 释放配额后它何时开始；③ 假 GPU 资源在 kubectl describe node 里怎么显示。

动手实验（家里电脑，周末半天）

以下命令未在本机运行验证。家里电脑一般没有 NVIDIA GPU 在 kind 中可用，所以用假的扩展资源 example.com/gpu 演示，它只是一个整数计数，没有真实设备。

1. Job 与 CronJob

kubectl create job pi --image=busybox -- sh -c 'echo hello; sleep 5'
kubectl get job,pod -w
kubectl create cronjob tick --image=busybox --schedule='*/1 * * * *' -- date
kubectl get cronjob,job -w      # 看几分钟后删掉：kubectl delete cronjob tick

2. 给节点通告假 GPU（官方“扩展资源”任务的方法）

kubectl get nodes                      # 选一个节点，下面记作 <node>
kubectl proxy &                        # 默认监听 127.0.0.1:8001
curl --header "Content-Type: application/json-patch+json" \
  --request PATCH \
  --data '[{"op": "add", "path": "/status/capacity/example.com~1gpu", "value": "2"}]' \
  http://localhost:8001/api/v1/nodes/<node>/status
kubectl describe node <node> | grep -A8 Capacity   # 应出现 example.com/gpu: 2

3. 安装 Kueue（官方文档当前版本 v0.20.4）

kubectl apply --server-side -f https://github.com/kubernetes-sigs/kueue/releases/download/v0.20.4/manifests.yaml
kubectl wait deploy/kueue-controller-manager -nkueue-system --for=condition=available --timeout=5m

未核实：Kueue 对 K8s 最低版本的要求，请以安装页为准；用最新 kind 默认节点镜像一般较新。

4. 配队列：总配额 1 个假 GPU

cat <<'EOF' | kubectl apply -f -
apiVersion: kueue.x-k8s.io/v1beta2
kind: ResourceFlavor
metadata: {name: default-flavor}
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: ClusterQueue
metadata: {name: cluster-queue}
spec:
  namespaceSelector: {}
  resourceGroups:
  - coveredResources: ["cpu", "memory", "example.com/gpu"]
    flavors:
    - name: default-flavor
      resources:
      - {name: cpu, nominalQuota: 4}
      - {name: memory, nominalQuota: 4Gi}
      - {name: example.com/gpu, nominalQuota: 1}
---
apiVersion: kueue.x-k8s.io/v1beta2
kind: LocalQueue
metadata: {namespace: default, name: user-queue}
spec: {clusterQueue: cluster-queue}
EOF

未核实：把 example.com/gpu 放进 coveredResources 是按 Kueue 配额文档的通用写法推断，官方示例只用了 cpu/memory。

5. 提交两个各要 1 个假 GPU 的 Job，看第二个排队

for i in 1 2; do cat <<'EOF' | kubectl create -f -
apiVersion: batch/v1
kind: Job
metadata:
  generateName: gpu-job-
  namespace: default
  labels: {kueue.x-k8s.io/queue-name: user-queue}
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: c
        image: busybox
        command: ["sh", "-c", "sleep 60"]
        resources:
          requests: {cpu: "100m", memory: 64Mi}
          limits: {example.com/gpu: 1}
EOF
done
kubectl get workloads,jobs,pods      # 一个 Job 运行，另一个挂起等待
kubectl describe clusterqueue cluster-queue

60 秒后第一个完成、释放配额，第二个应自动开始。对比：去掉 queue-name 标签直接提交，看只有节点调度器限制时会怎样。

回忆题（先答再展开）

  1. 设备插件怎样让 GPU 变成可调度资源？
    参考答案

    设备插件通过 kubelet 的 Registration gRPC 注册并上报设备列表，kubelet 在节点状态里通告扩展资源（如 nvidia.com/gpu），调度器据此按数量调度，Pod 在 limits 中申请。

  2. 扩展资源/GPU 的申请有哪些限制？
    参考答案

    只能是整数、不能超卖；GPU 只在 limits 中指定（只写 limits 时以它为 requests；两者都写必须相等；不能只写 requests）。

  3. Kueue 和 kube-scheduler 的分工？
    参考答案

    Kueue 决定作业是否准入（配额够才放行、可排队和抢占），通过管理 Job 的 suspend 实现；kube-scheduler 负责准入后每个 Pod 落到哪个节点。

  4. ResourceFlavor、ClusterQueue、LocalQueue 各是什么？
    参考答案

    ResourceFlavor 描述一类资源（可用节点标签对应不同硬件）；ClusterQueue 定义各 flavor 的配额；LocalQueue 是命名空间里的提交入口，指向一个 ClusterQueue。

  5. 一句话说 Slurm 与 K8s + Kueue/Volcano 的区别？
    参考答案

    Slurm 是为 Linux 集群原生设计的集群管理与作业调度系统；K8s 本身面向容器编排，靠 Kueue/Volcano 在其上补充排队、配额和批调度。
