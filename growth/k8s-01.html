模块1 · K8s 核心与 API 交互

建议第 1 周完成 · 工作日每天 30 分钟读讲义 · 周末前半天做实验 · 已完成 0 项

目标

能不看资料讲清：一个 Pod 从 kubectl apply 到跑起来经过哪些组件；为什么 K8s 是“声明式 + 调谐循环”；list-watch 和 resourceVersion 怎么让客户端低成本追踪变化。能用 kubectl 和 Java 客户端列出、创建、监听 Pod。

讲义 · 四栏卡片（读完一栏点 ✓）

是什么

控制平面：kube-apiserver（暴露 K8s HTTP API，是唯一入口）、etcd（保存全部 API 数据的一致、高可用键值存储）、kube-scheduler（为还没绑定节点的 Pod 选节点）、kube-controller-manager（运行各类控制器）。节点上有 kubelet（保证 Pod 及其容器在跑）和容器运行时。K8s 组件概览 ↗

Pod 是最小调度单位；Deployment 声明“要几个副本、用什么模板”；Service 给一组 Pod 一个稳定访问入口。

控制器是一个“控制循环”：盯住集群的当前状态，让它向期望状态靠近。K8s 控制器（控制循环） ↗

为什么这样设计

你只写期望状态（spec），由控制器不断对比实际状态（status）并修正，这就是声明式 + 调谐。好处：组件挂掉重启后再对比一次就能自愈，不依赖“某条命令一定执行成功”。K8s 控制器（控制循环） ↗

所有组件都只和 API Server 交互、不直接改 etcd，API Server 统一做鉴权、准入和校验。

list-watch：客户端先 list 拿到全量和集合的 resourceVersion，再从这个版本开始 watch 增量变化，避免反复轮询全量。每个对象都有 resourceVersion 字段。K8s API 概念（list/watch、resourceVersion） ↗ Java 客户端的 Informer 就是在 list-watch 之上加本地缓存。Java 客户端代码示例（Wiki） ↗

什么时候会出问题

  • watch 版本过旧：请求的 resourceVersion 已不可用时，API Server 返回 410 Gone，客户端必须重新 list 再 watch。K8s API 概念（list/watch、resourceVersion） ↗自己写 watch 循环不处理它，就会丢事件或死循环。
  • 直接轮询 list：大集群里频繁全量 list 会压垮 API Server，所以要用 Informer 缓存读。
  • 以为命令式改动会保留：手动改了 Deployment 管的 Pod，控制器会按模板改回去。
  • etcd 是单一事实来源：etcd 不可用时集群无法变更（已运行的 Pod 一般继续跑）。

未核实：etcd 故障时已运行 Pod 的具体表现，按经验描述，未在官方文档逐条核对。

怎么验证过

做完下面实验后自己填：① 删掉 Deployment 的一个 Pod，看它被重建（调谐）；② Java watch 程序打印 ADDED/MODIFIED/DELETED 的顺序；③ 用 kubectl get pod -v=6 看 kubectl 实际发出的 HTTP 请求。

动手实验（家里电脑，周末半天）

以下命令未在本机运行验证（本机没有 Docker），按官方文档整理。

1. 装 kind 和 kubectl，建集群

按 kind 快速开始 ↗ 和 kubectl 等工具安装 ↗ 安装（macOS 可用 brew install kind kubectl；Windows/Linux 见文档）。需要先装好 Docker。

kind create cluster            # 默认集群名 kind
kubectl cluster-info --context kind-kind
kubectl get nodes

2. kubectl 看声明式与调谐

kubectl create deployment web --image=nginx --replicas=2
kubectl get pods -l app=web -w      # 另开一个终端保持观察
kubectl delete pod -l app=web --wait=false   # 看控制器把 Pod 补回 2 个
kubectl expose deployment web --port=80
kubectl get svc,endpoints web
kubectl get pod -v=6                # 看实际 HTTP 请求

3. Java 客户端：列出 / 创建 / 监听 Pod

选官方 kubernetes-client/java（官方 Java 客户端） ↗（K8s 官方客户端库列表中的 Java 客户端）。Maven Central 当前最新版本 28.0.0。注意 README 说明：从 20.0.0 起 API 不向后兼容，可选参数合并为一个请求对象（调用以 .execute() 结尾），且不再支持 Java 8。

<!-- pom.xml -->
<dependency>
  <groupId>io.kubernetes</groupId>
  <artifactId>client-java</artifactId>
  <version>28.0.0</version>
</dependency>
import io.kubernetes.client.openapi.*;
import io.kubernetes.client.openapi.apis.CoreV1Api;
import io.kubernetes.client.openapi.models.*;
import io.kubernetes.client.util.*;
import com.google.gson.reflect.TypeToken;
import java.util.concurrent.TimeUnit;

public class PodLab {
  public static void main(String[] a) throws Exception {
    ApiClient client = Config.defaultClient();          // 读 ~/.kube/config
    client.setHttpClient(client.getHttpClient().newBuilder()
        .readTimeout(0, TimeUnit.SECONDS).build());     // watch 需要无限读超时
    Configuration.setDefaultApiClient(client);
    CoreV1Api api = new CoreV1Api();

    // 1) 列出（与官方 Example.java 一致）
    for (V1Pod p : api.listPodForAllNamespaces().execute().getItems())
      System.out.println(p.getMetadata().getNamespace() + "/" + p.getMetadata().getName());

    // 2) 创建（未核实：createNamespacedPod 新式写法）
    V1Pod pod = new V1Pod().metadata(new V1ObjectMeta().name("java-demo"))
        .spec(new V1PodSpec().addContainersItem(
            new V1Container().name("c").image("nginx")));
    api.createNamespacedPod("default", pod).execute();

    // 3) 监听（仿照官方 WatchExample.java，把 Namespace 换成 Pod）
    try (Watch<V1Pod> w = Watch.createWatch(client,
        api.listNamespacedPod("default").watch(true).buildCall(null),
        new TypeToken<Watch.Response<V1Pod>>(){}.getType())) {
      for (Watch.Response<V1Pod> e : w)
        System.out.println(e.type + " " + e.object.getMetadata().getName()
            + " " + e.object.getStatus().getPhase());
    }
  }
}

未核实：列出与 watch 写法来自官方 Example.java / WatchExample.java；createNamespacedPod 与 listNamespacedPod 的新式调用是照同一风格推断，未编译验证。

运行后，另开终端执行 kubectl delete pod java-demo，看 watch 打印的事件序列。进阶：官方示例里的 InformerExample（需要 client-java-extended 模块）演示 list-watch + 本地缓存，见 Java 客户端代码示例（Wiki） ↗。

产出：Java 程序能列出/创建/监听 Pod，写一张“list-watch 与 410 Gone”卡片

回忆题（先答再展开）

  1. kubectl apply 一个 Deployment 后，到容器跑起来，依次经过哪些组件？
    参考答案

    kubectl → kube-apiserver（鉴权/准入/校验，写入 etcd）→ Deployment 控制器创建 ReplicaSet → ReplicaSet 控制器创建 Pod → kube-scheduler 为未绑定 Pod 选节点并绑定 → 该节点 kubelet 通过容器运行时拉起容器并上报状态。

  2. 什么是调谐循环？为什么比命令式更能自愈？
    参考答案

    控制器反复比较期望状态和当前状态并采取动作使其靠近。即使中间失败或组件重启，下一轮对比仍会纠正，不依赖某条命令一次成功。

  3. list-watch 中 resourceVersion 起什么作用？
    参考答案

    list 返回集合的 resourceVersion，watch 从该版本开始推送之后的增量变化；每个对象也带 resourceVersion，标识其存储版本。

  4. watch 收到 410 Gone 怎么办？
    参考答案

    说明请求的版本已不可用（太旧），需要重新 list 拿新版本，再从新版本 watch。Informer 会自动处理。

  5. 为什么推荐用 Informer 而不是定时 list？
    参考答案

    Informer 只做一次 list 加持续 watch，读操作走本地缓存，显著减轻 API Server 压力，并能以事件回调方式响应变化。
